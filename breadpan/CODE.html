breadpan 实现骨架

1. 文件树

src/
├── lib.rs               # 公开面出口（核心 + gtk 整合层）
├── handle.rs            # TrayConfig + TrayHandle 前端（指令受理 → 内部线程投递）
├── events.rs            # TrayEvent、单事件通道（tokio mpsc；start 交付唯一 Receiver）
├── tracker.rs           # Item 登记簿记（最小集）：报到 / 反向发现 / 换主重绑定 / 死亡清理
├── props.rs             # 属性即时读取（zvariant/serde → 原生结构）
├── dbus/
│   ├── mod.rs           # DBus 域出口（内部聚合）：启动编排、报到受理与反向发现、全局信号订阅
│   ├── bus.rs           # 会话总线连接（zbus tokio 特性）与库内 tokio 运行时宿主
│   ├── watcher.rs       # 登记中心服务：名持有（不可替换）、所有权丢失上报、停机
│   ├── iface.rs         # org.kde.StatusNotifierWatcher 协议面（ARCHITECTURE §3.4）
│   ├── heartbeat.rs     # 周期存活探测：Item alive 回写 + 总线断连检测（IO 类错误 → Fatal）
│   ├── menu.rs          # dbusmenu 现场读取（零缓存·逐层懒加载）
│   └── interact.rs      # 语义输入路由（ARCHITECTURE §2.6）+ InteractionResult 回执
└── gtk/
    ├── mod.rs           # 整合层出口（渲染直出；主线程约束说明）
    └── paintable.rs     # 渲染直出：主题命中 → 主题图标；路径 → 文件纹理；未命中 → 位图纹理

examples/                # 唯一示例目录：可运行的用法实例（README「实例代码」表）
├── minimal.rs           # 最小消费方：start → 消费事件流 → 打印快照与事件
└── interactions.rs      # 交互与菜单：activate / scroll / menu()·menu_expand 现场读取 / menu_activate
  • 分组约定：dbus/ 收拢 DBus 域实现——总线连接、Watcher 服务与协议面、存活探测、dbusmenu 读取、交互路由；
  • 登记簿记与属性取数（tracker、props）留顶层；
  • handle/events 为公开前端。
  • 内部线程固定为 1——宿主 tokio CurrentThread 运行时，DBus 收发（zbus tokio 特性）、事件组装与投递全部在此异步线程完成，不创建线程池；
  • 事件通道为单实例 tokio mpsc（start 交付唯一 Receiver；消费端与执行器无关），消费端由消费方经 glib::spawn_future_local 驱动，库不创建 GLib 上下文。

2. 内部类型与方法签名

  • 按 src/ 文件树组织的内部类型与方法签名摘要；标注 //见 ARCHITECTURE … 的条目为架构文档已定义符号的统一引用格式；
  • 收录标准：只列 §3 调用栈引用到的核心类型与方法；条目只承载签名与一行用途——const 定义不收录（字面取值随实现调试浮动，取舍记录见 IMPLEMENTATION.md），方法内部步骤一律归 §3 调用栈，未列出者皆为局部实现细节；
  • 注意：登记合并（Upsert::Renamed / NameChanged，§3.3.1）、节流任务随栅栏启动（§3.2）、同名换主的 OwnerChanged 交付（§3.3.2）与 Menu 取值宽容化（menu_path_of + 解析失败不覆盖，§3.2）为 IMPLEMENTATION.md 记录的改进——dev 分支代码滞后于记录，冲突处以 IMPLEMENTATION.md 为准，不随源码回退；
  • 公开类型与签名（Tray / TrayHandle / TrayEvent / 数据模型 / TrayError / gtk）见 ARCHITECTURE.html §3，此处不重复。

pub(crate) struct ItemEntry {
    pub service: String,   // 服务名（= TrayItemId；知名名或唯一名皆可，临时唯一名占位可升级，§3.3.1）

  • 树形线条只承载两类行——具体方法调用与判断条件；
  • 每个调用至多后置一条注释，注释不挂枝（无 ├──/└──，所在层级竖线延续）；
  • 更长的动机与取舍写入块后正文。

3.1. 启动（start）

3.1.1. 总流程（bootstrap）

流程 Tray::start(config)（handle.rs）
├── EventQueue::new() → (Arc<EventQueue>, 唯一 Receiver)
├── BusParts::new(config, events)
├── BusCenter::spawn_runtime(parts)
│    └── mod::run(bus, stop_rx, fatal_rx, displaced_rx, ready_tx)
│         └── bootstrap(bus)（顺序即契约，理由见下方说明段）
│              ├── watcher::mount_interfaces(bus)?
│              │    // org.kde / org.freedesktop 两前缀挂同一路径；名未在位则报到无从发生
│              ├── spawn_signal_tasks(bus)
│              │    // 6 条 match rule 常驻任务（NOC / New*×2 / PropertiesChanged×2 / dbusmenu，经 pump_signal_stream 订阅，§3.2 §3.3.2 §3.4.2）
│              ├── bus.spawn(heartbeat::heartbeat_task(bus))（§3.6）
│              ├── discover_existing(bus)（§3.1.2）
│              ├── queue_snapshot(bus)（§3.1.3）
│              ├── bus.spawn(debounce_task(bus))（§3.2，栅栏置位后启动）
│              └── watcher::WatcherService::start(bus)?
│                   // 已被他人持有 → NameTaken（多 Watcher 不能共存）
├── ready_rx.try_recv()（轮询至 bootstrap 结果）
│    // 引导总时限 max(10×timeout_ms, 10s) 守护；超时/失败 → join 内部线程并返回 Err
└── return (TrayHandle{Arc<RuntimeShared>}, 事件通道 Receiver)
  • Watcher 名最后申请——申请前报到无从发生，快照投递后所有报到以增量事件衔接（首事件即快照、无重叠无缺口）；若先申请名，等待 Watcher 出现的 Item（如 clash-verge）会在快照收集前报到，其 Added 抢在快照之前——实测复现；
  • 订阅（spawn_signal_tasks）与存活探测（heartbeat_task）先于申请名同理：名在位即可能收到信号与超时，须先就位才不丢；
  • 节流任务（debounce_task）不在此列——其交付始于快照之后，随栅栏置位启动（§3.2）。

3.1.2. 反向发现（存量 Item 双级探测）

内部: dbus::discover_existing(bus) → Vec<String>
├── bus.call(ListNames) → 过滤 org.kde.StatusNotifierItem- 前缀候选
├── probe_item_iface(bus, name) → Result<bool>（逐候选）
│    ├── bus.call(Introspect(name, /StatusNotifierItem))
│    │    // 第一级：应答 XML 含 SNI 接口名（org.kde / org.freedesktop 任一）→ 确认
│    └── props::read_all(name, /StatusNotifierItem)
│         // 第二级：前者失败或应答无接口名时到达（Electron/CEF 不响应 Introspect，QQ 音乐实测）；Ok = 确认
├── 确认？ → dbus::register_item(bus, name, sender=None, announce=false)
│    // 静默入册：不广播、不入队 Added——快照是首事件（§3.3.1）
└── 未确认 / 探测失败？ → 记入过程叙述，不中断发现循环

3.1.3. 快照投递与栅栏（queue_snapshot）

内部: dbus::queue_snapshot(bus) → Vec<String>（返回值快照后以 Narration 事件交付）
├── ItemTracker::all() → Vec<ItemEntry>
├── bus.rt.spawn(|| props::fetch_item(bus, entry))（逐条并发）
│    // fetch_item = read_all + tray_item_from_props（宽容取值归一化，§2.5）；单个读取失败 → 记过程叙述，该 Item 不入快照
├── items.sort_by_key(id)
│    // 发现序不稳定，排序保证确定性输出
├── events.send(TrayEvent::Snapshot{items})
├── bus.mark_snapshot_done()
│    // 与入队之间无 await：单线程运行时内不可分割，不存在「快照已入队、栅栏未置位」中间态
└── bus.take_deferred_removed() → Vec<TrayItemId>（逐条 events.send(Removed(id))）
     // 仅快照内 id 补投；快照外按从未出现丢弃
  • 栅栏是各事件源「首事件即快照、无重叠无缺口」的兜底：报到（§3.3.1）、NameOwnerChanged（§3.3.2，同名换主与死亡清理）、菜单变更（§3.4.2）按栅栏前/后记录行为分支；
  • 变更节流任务在置位后才启动（§3.2），Changed 天然不早于快照；
  • 栅栏为防御性——申请时序（§3.1.1）使栅栏前报到在正常路径上无从发生。

3.2. 变更通告合并（固定窗口节流）

内部: properties_changed_task(iface)×2 / item_signals_task(iface)×2
     // kde 与 fd 前缀各一条常驻任务，经 pump_signal_stream 订阅消费
├── find_by_signal(发送者唯一名, 对象路径) → Option<TrayItemId>
│    // (唯一名, 路径) 唯一命中（双注册已并入，§3.3.1）；未命中 → 丢弃
├── ItemTracker::update_routing(&id, menu, menu_only)（仅 PropertiesChanged）
│    // menu = props::menu_path_of(v)（对象路径/字符串两形态 + ObjectPath 规范校验，§2.5）：解析成功才传 Some——失败传 None 忽略本次更新、保留旧值（Menu 键被清空 = 右键跌回 fallback + MenuChanged 永久静默）；menu_only 非 Bool 变体同则
├── pending.insert(id)
│    // 仅记入待通告集合；无计时重置——连发不推迟交付
└── debounce_task 固定节拍到期 → pending.drain()（逐个 events.send(Changed(id))）
     // 每 debounce_ms 一次，与信号无关；栅栏置位后启动（§3.1.3）；单通道，满则丢弃
  • 合并针对的是重读放大：Item 侧的双重上报（New* 与 PropertiesChanged 并发、状态切换伴随连发）与进度型 Item 的高频刷新，经零缓存架构放大为消费方的重复现场读取——窗口节流把重读频率压到每 Item 至多 1 次/窗口；
  • 事实事件幂等，窗口内折叠不丢信息。

3.3.1. 报到（RegisterStatusNotifierItem 受理）

               └── 否 → 静默入册

3.3.2. NameOwnerChanged（同名换主 / 死亡清理）

内部: name_owner_changed_task 收到 NameOwnerChanged(名字, 旧属主 → 新属主)
├── 名字 == Watcher 名？ → 所有权丢失（§3.7.1）
├── 新属主 ≠ ""？ → 同名换主（应用重启直接顶名）

3.5. 输入路由与回执

3.5.1. 左键（同步路径与 Menu 回退）

流程 left_click(id) / left_click_at(id, 0, 0)
├── input(id, Input::Left) → bus.cmd(interact::route)
│    // 同步桥：rt.spawn 派发命令 future 至内部运行时 + std::sync::mpsc 阻塞等待（守卫 sync_guard_ms，超时语义见下方）；禁 rt.block_on（CurrentThread 运行时由内部线程驱动，跨线程并发 block_on 属未定义行为）
├── bus.entry_of(id) → ItemEntry
│    // 不在册 → ItemNotFound
├── menu_only && DBusMenu 在册？ → menu::read_layer(...)（§3.4.1）→ return Outcome::Menu
└── interact::invoke_xy(entry, Activate, (x, y))
     // 就地等待往返
     ├── Ok → events.send(InteractionResult{Activate, Ok})；return Outcome::Dispatched
     ├── Err(超时)？ → return Err
     │    // 对端主循环失联：menu 同一主循环分发亦不可读——不跨前缀重试、不回退
     ├── Err(非超时) && DBusMenu 在册？ → menu::read_layer(...)（§3.4.1）→ return Outcome::Menu
     │    // 回退无回执事件
     └── Err(非超时) 无菜单 → return Err
  • libappindicator 系 Item 的 Activate 无处理器——XML 静态声明但分发 catch-all，不可预先探测（Introspect 说谎、探测调用会误触激活）；
  • 左键出菜单是宿主侧既定策略：菜单由宿主经 dbusmenu 渲染，不依赖 Item 端激活；
  • 回退分支的失败形态为同步快失败，与超时无关。
  • 命令 future 内每个执行步骤（DBus 调用）自持 timeout_ms 上界；
  • 桥的阻塞等待受 sync_guard_ms 守卫（默认 30000 ms，推荐 ≥ timeout_ms×4 + 10s 以覆盖最长的多步流程——当前最长为 menu 流程 3 连调用）；
  • 守卫到期 → TrayError::Hung：内部未在守卫内完成——运行时楔死或守卫配置过低，处置为重建或调大守卫（与 Timeout 的「对端慢，可重试」语义不同类）；
  • 通道断开且已停机 → Stopped；
  • 守卫值不由执行路径推算——路径会变化，推算值静默失效（初版的 4×timeout+10s 即属此类，经裁决改为消费者可配置）。

3.5.2. 其余语义输入（受理即返回）

流程 middle_click(id) / right_click(id) / scroll_up(id) 等及其 _at / _by 变体

├── bus.entry_of(id) → ItemEntry
│    // 不在册 → ItemNotFound
├── interact::route(id, input)
│    // 依据登记簿记 menu / menu_only 路由，零查询
│    ├── right_click？
│    │    ├── DBusMenu 在册 → Menu 流程（§3.4.1）
│    │    └── 否则 → invoke_xy(entry, ContextMenu, (x, y))
│    ├── middle_click → invoke_xy(entry, SecondaryActivate, (x, y))

│         // invoke_*：org.kde 前缀优先，非超时失败回退 org.freedesktop（兼容只导出规范原文拼写的少数实现）；任一侧超时 → 立即报错；双前缀俱败 → 合并上报两侧错误

└── events.send(InteractionResult{op, result})

3.6. 存活探测循环

3.7.1. 所有权丢失（Displaced）

          // 终局报错：被其它 Watcher 取代；不重试、不强制夺回

3.7.3. Fatal（总线断连）

     ├── ItemTracker::clear()
     ├── bus.set_stopped()
     ├── events.send(Fatal(msg))；events.close()
