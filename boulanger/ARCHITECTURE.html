boulanger 架构规格

本文档面向实现者：接口契约、时序图、数据模型。 能力边界以 README.html 为权威，类型与签名见 CODE.html。

1. Watcher 角色与接口契约

SNI 世界里必须有人在总线上扮演 org.kde.StatusNotifierWatcher（登记中心）， Item（图标提供方）与 Host（图标展示方）据此互相感知。本库实现该角色的服务端侧， 通信全部发生在会话总线。协议面即本库的对外接口契约：

DBus 成员类型语义
RegisterStatusNotifierItem方法Item 报到：登记总线唯一名 + 对象路径；重复报到幂等
RegisterStatusNotifierHost方法Host 报到：登记展示方
IsStatusNotifierHostRegistered方法查询：Host 是否已登记
RegisteredStatusNotifierItems方法查询：当前在册 Item 清单
StatusNotifierItemRegistered信号广播：Item 报到
StatusNotifierItemUnregistered信号广播：Item 离开

进程内组装侧的契约：仅暴露服务启动 / 停止形态（启动产出服务句柄；停止幂等；句柄 drop 自动停止）， 不暴露任何回调或数据面。

2. 服务实现规则

2.1 名持有

  • 在会话总线申请持有 org.kde.StatusNotifierWatcher 名字，允许被替换（allow-replacement）；
  • 被顶替（NameLost）时视为让位：清理自身簿记，对外呈现为服务已停止；
  • 让位语义使环境级 Watcher（如桌面自带的）可以随时接管。

2.2 登记受理与查询

  • Item 登记：记录"唯一名 + 对象路径"；Host 登记：记录展示方；
  • 查询接口按 §1 协议面如实应答；簿记只在内存，不落盘。

2.3 登记广播

  • Item 报到 / 离开各广播一类信号（§1）；Host 变更通过查询接口暴露，不广播；
  • 广播是本库唯一的数据输出——观察方（托盘客户端等）据此感知托盘世界的变化。

2.4 死亡清理

  • 监听总线 NameOwnerChanged：持有者唯一名消失（进程退出/崩溃）即移除其登记并广播 Unregistered；
  • 本库自身退出/崩溃时，总线名随连接消失，等同角色下线——无残留簿记。

3. 数据模型（登记簿记）

簿记条目内容生命周期
在册 Item 表总线唯一名 + 对象路径报到时插入（幂等）；唯一名消失或主动注销时移除并广播
在册 Host 表展示方标识报到时插入（幂等）；唯一名消失时移除（不广播）

簿记只在内存；本库只维护"谁在"，不维护"什么样"——Item 属性/图标/菜单等数据面归客户端侧， SNI 数据通路不经 Watcher。

5. 运行形态

形态实现规格
进程内组装（默认）服务启动/停止形态（§1）；不暴露回调或数据面；句柄 drop 自动 stop
独立常驻（bin）main 持有服务直至 SIGINT/SIGTERM；适用于"Watcher 活得比展示方久"的部署——展示方重启不引发 Item 全量重注册

6. 依赖约束

  1. 不依赖项目群任何其他模块（workspace 内零反向依赖）；
  2. 依赖白名单仅限：zbus（DBus 通信，含服务端能力）、thiserror（错误定义）、标准库；
  3. 零 GTK、零 UI 依赖——服务端角色与框架无关；
  4. 必须独立编译测试（构建与 CI 见 BUILD.html）。

7. 测试与验收

场景断言
登记往返dbus session 内：Item/Host 登记 → 查询接口如实应答 → 广播信号按序到达
死亡清理持有者连接断开后，其登记被移除且广播 Unregistered
让位/替换外部 Watcher 申请同名时本库让位，簿记清空、服务停止形态如实呈现
客户端互通客户端在位并登记 Host 后，其 Watcher 跟踪应呈现在位；本库停服后应呈现在位消失
