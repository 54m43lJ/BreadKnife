BreadPan / Boulanger 项目结构与边界总览

本文档提取自《BreadPan / Boulanger 文档体系生成任务》中定义项目结构、项目关系与各项目边界的部分，作为核心文档及其余文档的骨架。
每个组件章节固定两节：定位（该项目自身的设计取舍）与边界（功能/特性覆盖范围与以业务语言描述的暴露面，不涉及 API 签名）。

1. 项目身份

项决策
项目构成breadpan（SNI/DBusMenu 托盘客户端库）+ boulanger（SNI Watcher 角色库）+ demo-tray（人工验收工具）
命名逻辑breadpan = 烤盘（承放、供取用）；boulanger = 法语面包师（照看炉火、收发面团＝登记 Item）
发布状态暂不发布 crates.io；版本策略照常（SemVer）
使用场景Wayland 会话；强绑定 GTK 框架（整套项目以 GTK 编写，不做跨框架移植）
目录形态同一 workspace 平行 crate；breadpan ⊥ boulanger，互相零依赖

4. breadpan

定位

无头的 SNI 协议客户端库 + DBusMenu 客户端库，以统一事件流交付托盘世界的全部变化。 独家支持 GTK，为 GTK 应用提供深度整合（渲染对象直出 + 事件桥接方案）。

自身设计的核心取舍：

  • 库不拥有 UI：无窗口、无布局、无事件循环——渲染逻辑归消费方，但数据形态为 GTK 深度定制；
  • 不实现 Watcher 角色：该职责归属 boulanger，breadpan 仅作为客户端观察其存亡；
  • 零菜单缓存：对菜单不储存任何状态，一致性代价 >> 缓存收益；
  • 零下游词汇：文档与概念体系不包含任何具体消费方（任务栏/panel 等）的概念，从未见过下游项目的人可无障碍使用。GTK 是框架绑定，不算任务栏耦合；
  • 依赖取向：zbus + thiserror + gtk4 + std，无日志门面——库自身状态经事件流汇报，日志是消费方职责。框架绑定落在 gtk4 白名单，是「强绑定 GTK」决策在依赖层的落地。

边界

功能覆盖（做）

功能域覆盖内容
Item 生命周期跟踪托盘图标的出现 / 消失 / 属性变更，以事件流与状态快照两种方式交付；Host 登记与 Item 跟踪均为客户端职责，由本库承担
图标与提示交付图标名称与位图双路交付；overlay / attention / tooltip 图标同类型全覆盖；提供主题命中与位图回退的渲染直出
菜单数据交付菜单布局与条目属性的现场拉取（含助记符解析与原始值逃生门）；菜单变更信号的转发。菜单渲染本身不在此列（见下）
交互转发激活、次级激活、滚轮、菜单条目触发、弹出前通知——作为指令转发给对应 Item
健康呈现心跳探测 Item 存活状态并如实呈现（只标记，不移除）
GTK 深度整合渲染对象直出（主题命中 → 主题图标；未命中 → 位图纹理）与事件桥接权威方案

暴露面（业务语言）

  • 事件流：Item 生命周期事件、属性变更、菜单变更、Watcher 存亡变迁、内部过程叙述与终止宣告；
  • 状态快照：订阅时刻的完整 Item 记录与 Watcher 存在性，与事件流原子配对、无重叠无缺口；
  • 交互指令：对 Item 的各类激活/滚动/菜单操作，同步给出成功或失败结论；
  • 菜单现场读取：每次读取即最新全量布局；
  • GTK 渲染入口：图标 → 可绘制对象的一次性转换（须在 GTK 主线程使用）；
  • 测试替身：内置最小 Watcher 替身与演示 Item，保证 CI 在裸会话下自足（与 boulanger 不构成重复）。

功能覆盖（不做）

不做理由
拥有任何 UI（窗口/布局/事件循环）渲染逻辑归消费方
XEmbed/X11 传统托盘场景钉死 Wayland
菜单渲染/弹出定位只交付菜单数据模型与激活通道
AttentionMovieName实际使用者寥寥，进「已知不实现清单」
异步运行时泄漏公开面零 async，内部执行模型对使用者不可见
菜单缓存零缓存零状态，一致性代价 >> 缓存收益
移除无响应 Item / 强制退出无响应应用移除权专属唯一名消失；SNI 不暴露 pid，协议层无通路——强制退出的正当归属是 WM/系统监视器
日志门面日志经事件流由消费方自行管理

5. boulanger

定位

SNI Watcher 角色的纯服务端小库；无 UI。规模预期 300–500 行。

自身设计的核心取舍：

  • 纯登记簿角色：只做「谁在托盘世界」的登记与广播，不接触任何业务数据；
  • Watcher 角色的专属归属：该角色从 breadpan 移除——那里的 Fallback 实现是生产路径死代码，且引发总线名争抢；角色独立后，多实例仲裁问题随之蒸发；
  • 由消费方进程内组装：作为独立 crate 被引入消费方进程运行；留有后门——加上 main 即可独立常驻进程（Watcher 活得比面板久，可避免面板重启引发的 Item 重注册风暴）；
  • 与 breadpan 正交：显式声明互不依赖；breadpan 自带的测试替身不构成重复；
  • 依赖取向：zbus + thiserror + std（无 gtk4——服务端角色与框架无关）。

边界

功能覆盖（做）

功能域覆盖内容
Watcher 名持有在会话总线上持有 Watcher 名字，让托盘世界知道"有 Watcher 在"（允许被替换/让位）
登记受理受理 Item 登记（图标提供方报到）与 Host 登记（图标展示方报到）
登记查询应答"Host 是否已登记""当前有哪些 Item"的查询
登记广播Item 报到/离开时对外广播，供观察方感知托盘世界的变化
死亡清理持有者消失（进程退出/崩溃）时自动清理其登记簿记

暴露面（业务语言）

  • 向会话总线提供一组登记与查询服务：Item/Host 报到、报到状态查询、当前在册清单查询；
  • 对外发出 Item 报到 / Item 离开两类广播信号；
  • 进程内组装时以服务启动/停止的形态暴露，不涉及任何回调或数据面。

功能覆盖（不做）

不做理由
任何 UI纯服务端角色，无渲染职责
Item 属性跟踪 / 图标 / 菜单等数据面SNI 数据通路不经 Watcher，数据面归 breadpan（客户端侧）
GTK 绑定服务端角色与框架无关，白名单不含 gtk4

6. demo-tray

定位

外围人工验收与调试工具；本仓库内唯一展示两库用法的文档载体；不是库文档的一部分。

自身设计的核心取舍：

  • 示范真实用法：以消费方视角组装两库（先启动 boulanger 服务，再连接 breadpan），示范代码即文档；
  • 诚实呈现：示范"客户端如实呈现库所报状态"的规范做法（如无响应 Item 置灰、内部叙述流展示）；
  • 不受"零下游词汇"约束：它是下游，是词汇约束的检验出口。

边界

功能覆盖（做）

功能域覆盖内容
渲染示范GTK4 简单窗口内的卡片渲染（经深度整合的渲染直出路径）
交互复现左键激活（含"整项即菜单"时的菜单行为）、滚轮、右键弹出菜单（弹出前通知 → 现场拉取 → 弹出 → 条目触发）、popup 打开期间菜单变更重取
事件观察底部事件日志展示全部事件类型（含内部过程叙述）
状态呈现示范无响应 Item 置灰呈现（示范"诚实状态呈现"）
内置测试台驱动演示 Item 制造全部变化；持有/释放 Watcher 角色制造存亡变迁

暴露面（业务语言）

  • 运行入口：一条运行命令即可在本地会话中启动；
  • 验收场景：纯 Hyprland（无任何托盘环境）下，从窗口内复现全部事件类型——这是三库协作的人工验收基准。

功能覆盖（不做）

不做理由
生产级托盘 UI外围验收工具，不追求产品化
进入库文档体系用法文档仅存在于本工具，库文档保持零下游词汇
